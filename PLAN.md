# Implementation plan

A step list for building taylr 1.0 against the specification in SPEC.md, written so a model with less context can execute it without making design decisions. Every step says what to create, what it depends on, and what "done" means.

## How to use this plan

SPEC.md and the published docs at [taylr.sh](https://github.com/brightdigit/taylr.sh/tree/main/src/content/docs/docs) are the source of truth; this plan only orders the work. When the plan and the docs disagree, the docs win and the disagreement is reported, not resolved.

Rules for the executing model:

- Do the steps in order within a phase. Phases 1 and 2 can run in parallel; nothing else can.

- A step is done only when its "Done when" line is true and `swift build` and `swift test` pass for the affected package. Never mark a step done with failing or skipped tests.

- Do not add a dependency, a package, a public type or a CLI flag that this plan or the docs do not name. If one seems needed, stop and ask.

- Do not change the docs or the spec. Report anything that looks wrong as a question.

- Every public type in `TaylrDescription` gets a doc comment, because DocC publishes it.

- Swift 6 language mode, strict concurrency, Swift Testing (never XCTest), `swift-format` and SwiftLint clean. Tests follow the suite conventions in the repo's `AGENTS.md`.

- No secrets, Apple IDs, team IDs or real org names in tests or fixtures; use `Acme`, `com.acmecorp`, `ABCDE12345`.

- Report at the end of each step: what was created, test count, anything deferred and why.

## Phase 2: model packages

Runs anywhere. Can run in parallel with Phase 1. Each package models one file format as `Codable` Swift types and nothing else: no knowledge of taylr, no file I/O beyond encode/decode to `Data`. Every package has the same test shape: encode a value, decode it, compare equal; decode a real-world fixture file checked into `Tests/Fixtures/`, re-encode, compare to the fixture (key order and formatting as the encoder produces them, so the fixtures are normalized once).

Fixtures come from real repos: AtLeast's and MistKit's `.github/workflows/*.yml`, `.mise.toml`, `.swiftlint.yml`, `.swift-format`, `.devcontainer/devcontainer.json`. Copy them in verbatim before writing any type, and model what they contain, not the whole upstream schema.

Handoff points: after 3.8 (the first time a Mac is needed), after 4.4, and before 5.4. At each handoff the Linux side pushes a branch with green CI and a short `HANDOFF.md` listing what is untested on macOS; the Mac side runs the Mac-only steps and deletes `HANDOFF.md` when they pass.

Suggested model split: a less expensive model for Phases 0–2 and the mechanical parts of 3 and 4, where every type is specified and tests are mechanical; a stronger model for 3.6 (workflow assembly, the one place with real reasoning about CI shape), 4.4 (validate rules) and 5.4 (debugging the end-to-end run).
